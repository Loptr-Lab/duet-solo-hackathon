# The Weaver — Shared Mechanics Instantiation

**Status:** Experimental host implementation. Not Veiled Dominion four-player canon.
**Shared mechanics host:** `Loptr-Lab/veiled-dominion-engine`
**Source authority:** `docs/design/WEAVER_START_HERE.md`, `docs/design/dueling-systems.md`, and related Weaver design/provenance material.

## Purpose

This document instantiates The Weaver's documented Systems Quartet / dueling mechanics against the reusable shared mechanics layer.

It does **not** define a new Weaver canon, resolve the open design questions in the Weaver handoff, or promote the experimental Weaver work into Veiled Dominion's four-player rules.

## Authority

The Weaver material explicitly describes the Systems Quartet card conversion and several dueling questions as open design work. The shared mechanics layer supplies reusable mechanics vocabulary only.

Therefore:

- The Weaver remains an experimental host implementation.
- The Systems Quartet remains host-specific.
- The Sufi Tariqah deck remains host-specific.
- The 52 Cards of War remains host-specific.
- Unresolved design questions remain unresolved.
- Veiled Dominion's canonical rules remain authoritative only within Veiled Dominion.

## 1. Shared State

Shared primitive: **State**.

The Weaver host state may contain:

- the two players / decks;
- each player's current hand/deck/discard state;
- the current board or card-resolution state when applicable;
- the shared conflict resource once Issue 1 is resolved;
- active cross-system effects;
- union/united state when the host mode requires it;
- event/result metadata.

The exact schema remains open where the source material marks it open.

## 2. Shared Actors

Shared primitive: **Actor**.

The Weaver's documented actors are player/system sides rather than Money Game factions.

Generic mapping:

| Shared Actor field | Weaver instantiation |
|---|---|
| Identity | Weaver participant / deck identity |
| State | hand, deck, discard, current system state |
| Capabilities | documented deck/system abilities |
| Constraints | host rules and unresolved interaction boundaries |
| Objectives / behavior | current game mode's win/cooperation objective |
| Available actions | legal card, board, conflict, or cooperation actions |

### Systems Quartet

The Systems Quartet supplies four distinct host-specific systems:

- Cannon — Biome / Homeostasis / Equilibrium behavior
- Coulter — Cybernetic Loop / positional pull
- Veblen — Leisure Class / selective targeting
- Fresco — Abundance / repurposing rather than capture

These are not generalized into the shared Actor contract.

## 3. Actions

Shared primitive: **Action**.

The documented Weaver handoff supports several action families:

```text
player/system intent
        ↓
host legality check
        ↓
resolve against current state
        ↓
state transition + result
```

Examples include:

- playing a card;
- using a documented suit/faction ability;
- generating or spending the eventual shared conflict resource;
- resolving a contested square;
- executing a cross-system cooperative effect;
- resolving an impasse through War.

Only actions explicitly adopted by the host rules are legal. The open design handoff does not become a rule merely because it appears in this document.

## 4. State Transitions

Shared primitive: **State Transition**.

The Weaver host can express its documented conflict and cooperation directions as:

```text
Current Weaver State
        +
Player/System Action
        ↓
Host-specific resolver
        ↓
Next Weaver State
        +
Result/Event metadata
```

### Conflict direction

The documented Issue 1 direction proposes a shared resource generated by different systems and used to resolve conflicts between systems that otherwise do not naturally interact.

**Status: OPEN DESIGN — not yet a numerical or named rule.**

### Cooperation direction

The documented Issue 2 direction proposes cross-system pairings that produce joint effects neither side can produce alone.

**Status: OPEN DESIGN — not yet a rule set.**

## 5. Causal Event Chain

Shared primitive: **Event → Outcome → Reaction → Counterreaction**.

For The Weaver, the event source is not required to be an external economic event.

Possible host event sources already supported conceptually by the handoff include:

- a card action;
- a system/faction condition;
- a contested square;
- a conflict-resolution result;
- a cooperative combination;
- an impasse requiring War.

These become actual triggers only when the corresponding host rule is resolved.

## 6. Cascades

Shared primitive: **Cascade**.

The Weaver can use cascades for interactions where one system's resolution creates another system response.

```text
Trigger
  ↓
System outcome
  ↓
Other system reaction
  ↓
Counterreaction
  ↓
Further state change
```

However, the Weaver source does not currently specify numerical cascade depth, concurrency, or termination parameters.

Those remain host-level open design decisions.

## 7. War as a Resolution Mechanism

The Weaver source documents a simple War resolution between the two personal decks when the players reach an impasse.

This can instantiate the shared Action / State Transition primitives:

```text
Impasse detected
      ↓
War resolution
      ↓
Winning side resolves the dispute
      ↓
Continue host state
```

War is therefore a host-specific resolution mechanism, not a shared primitive.

## 8. Presentation Boundary

The Weaver's interface may render:

- the current system/deck state;
- conflict and cooperation outcomes;
- card identities and lore;
- War resolution;
- cross-system effects;
- the state of the relationship between the two systems.

Presentation does not independently determine outcomes.

Authoritative resolution belongs to the host implementation.

## 9. What Is Deliberately NOT Instantiated

The following are not silently resolved:

1. The exact shared conflict resource.
2. How each system generates that resource.
3. How each system spends it.
4. The exact cross-system combo catalogue.
5. The final Systems Quartet card mapping.
6. Pip-card thematic progression.
7. The mechanical relationship between personal decks and the 52 Cards of War.
8. Any new Veiled Dominion four-player rule.

These are source-identified open design questions.

## 10. Relationship to Veiled Dominion

The shared mechanics layer lives below both host systems.

```text
                 SHARED MECHANICS
                        │
          ┌─────────────┴─────────────┐
          │                           │
      MONEY GAME                 VEILED DOMINION
          │                           │
                                  The Weaver*
```

* The Weaver's documented experimental mechanics are hosted in the Duet/Weaver design space and do not become four-player Veiled Dominion canon by this mapping.

The shared layer therefore permits reuse without requiring the Weaver to become a Veiled Dominion rules subsystem.

## 11. Safety / Promotion Gate

A Weaver mechanic may be promoted into an implementation only when:

- the host rule is explicitly resolved;
- its state inputs and outputs are deterministic;
- its interaction with existing Weaver rules is specified;
- presentation is separated from resolution;
- it does not silently alter Veiled Dominion canon;
- any promotion into Veiled Dominion is separately approved through Veiled Dominion's canon process.

## Result

The Weaver is now **structurally instantiated** against the shared mechanics vocabulary without pretending that its unresolved design questions have been answered.

The next actual game-design work is therefore concrete: resolve Weaver Issue 1 (shared conflict resource) and Issue 2 (cross-system cooperation), then encode those decisions as host-specific mechanics.
